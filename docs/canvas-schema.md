# Vault format

This document formalizes what a Histos vault contains, on top of the [JSON Canvas 1.0](https://jsoncanvas.org/spec/1.0/) format: the canvas, the cards' frontmatter, `histos.config.yaml`, the evals and the event log. Each has a machine-checkable JSON Schema, packaged with the CLI — [canvas](../src/histos/schema/histos-canvas.schema.json), [frontmatter](../src/histos/schema/histos-frontmatter.schema.json), [config](../src/histos/schema/histos-config.schema.json), [events](../src/histos/schema/histos-events.schema.json) — and `histos validate` checks all of them; here's the why.

What a schema **can't** check on its own — that each edge's `fromNode`/`toNode` point to an `id` that exists, and that the dependency graph is acyclic — the CLI checks too (`histos status` / `histos validate`).

A complete vault to look at: [`examples/sample-paper/`](../examples/sample-paper/), generated by [`scripts/make_example_vault.py`](../scripts/make_example_vault.py) with the real commands, so it's always exactly what Histos writes.

## Folder structure

```
<vault>/
├── project.canvas
├── content/
│   └── <id>.md              # one card = one file (its current, approved version)
├── proposals/
│   ├── <id>.md              # a draft waiting for approve/reject
│   ├── plan.yaml            # a pending plan of cards (v3.1)
│   └── guides/              # a pending change to PROJECT.md or ARCHITECTURE.md
├── approved/
│   ├── <id>.md              # the draft exactly as it was approved (rejected drafts are NOT kept)
│   ├── plans/               # every approved plan, by date (v3.1)
│   └── guides/              # each version of PROJECT.md / ARCHITECTURE.md an approval replaced
├── histos.config.yaml       # tier rules and evals settings (v3)
├── evals/                   # the evals run on every propose (v3)
├── PROJECT.md               # optional: what the project is
├── ARCHITECTURE.md          # optional: how it's written (style, conventions, stack)
├── AGENTS.md / CLAUDE.md    # instructions for the agent
├── .claude/settings.json    # Claude Code's deny list
├── .histos/                 # the event log (v3.1, see "Event log" below)
└── .histos.lock             # the vault lock (see below)
```

Vaults created before Histos's English rename use `propuestas/`/`aprobados/` instead of `proposals/`/`approved/` — same folders, same behavior, just the old names; the CLI detects whichever one a given vault already has and keeps using it, so existing vaults are never migrated automatically. Vaults created before v3 have no `histos.config.yaml` or `evals/` until `histos init --add-config`; without them, Histos behaves exactly as v2.

**`.histos.lock`** is created by the first command that changes the vault and stays there. Every such command holds an OS file lock on it from before it reads the vault to after it saves, so two agents working at once never overwrite each other's changes; the OS releases it even if a process dies. It's a plain file — Histos refuses to use it if it's a symbolic link. Obsidian ignores it (it starts with a dot), and if you keep a vault in git, add it to `.gitignore`.

Additional subfolders inside `content/` (e.g. `drafts/`) remain open — not part of this convention yet.

## Node types

Histos uses three of JSON Canvas's four node types:

- **`file`** — a task card. Points to a real `.md` in `content/`; never contains embedded text. A loose `link` node is not allowed.
- **`group`** — a purely geometric grouping (e.g. "chapter 3"). A node "belongs" to a group only if its coordinates fall inside the group's rectangle — there's no `parent_id` in the data. Carries no status. Groups whose `id` starts with `histos:` — `histos:unconnected` ("Not connected") and `histos:done` ("Done") — belong to `histos arrange`, which deletes and recreates them every time it runs (`:` can't appear in a card id, so they never collide with one). Any other group is yours and Histos never touches it — but `arrange` moves cards without looking at your groups, so a card can end up outside a group it used to sit in.
- **`text`** — only for decorative/documentation content (the color legend that `histos init` places on every new canvas). Not a card: the CLI ignores it entirely — all status/dependency logic explicitly filters by `type == "file"`. Nothing stops you from adding more text notes by hand in Obsidian; Histos simply doesn't touch them.

## Id convention

A card's `id` is the same slug as its file name: id `cap3` → `content/cap3.md`. Ids are letters, digits, `_` and `-` only. This keeps the CLI's own examples (`histos assign cap3`, `--depends-on cap2`) directly readable. A type prefix (`dec-`, `cod-`, `doc-`...) is a useful convention, not a rule: it makes the board easier to read and lets evals target card types with `only`/`except` (see [Evals](#evals)). `group` nodes only need to be unique, no further convention.

A card's `file` must sit directly in `content/`: no `/`, `\` or `:` in the name. On Windows a backslash is a path separator too, so `content/..\..\x.md` would point outside the vault; the schema refuses it, and the CLI double-checks that every card's resolved path is inside `content/` before touching it.

## Color → status

A card's color (the `color` field, preset `"1"`–`"6"`) **is** its status — never duplicated anywhere else:

| Preset | Color | Status |
|---|---|---|
| `"1"` | red | Blocked |
| `"2"` | orange | In progress |
| `"3"` | yellow | Proposal pending review |
| `"4"` | green | Approved |
| `"5"` | cyan | Dependency change request |
| `"6"` | purple | Backlog |

A `file` card without `color` isn't managed by Histos (added by hand in Obsidian, or corrupted data) — the schema rejects it because `color` is required on `cardNode`, and that's intentional: the schema validation itself is the detection mechanism.

**Blocked is a derived status**, not something the agent or the human assigns by hand: the CLI computes it by checking whether *all* of a card's incoming edges point to nodes already Approved (color `"4"`). Nothing stops you from setting color `"1"` manually, but the CLI treats that as a signal to recompute, not as a source of truth.

**Dependency change request (`"5"`) is reserved:** it's part of the legend, but no command sets it yet — in practice the agent asks for authorization in the conversation (`AGENTS.md` rule 4) and then passes `--authorized`. A card only turns cyan if someone sets that color by hand; `histos status` and the desktop app still list it under its own heading, and the CLI never recomputes it.

## Edges — dependency semantics

`fromNode → toNode` means **"toNode depends on fromNode"**: fromNode must reach Approved before toNode can leave Blocked. This matches the canvas's left-to-right, Gantt-style layout and the spec's default (`toEnd` = `"arrow"` points at toNode, i.e. at whatever gets unblocked).

**Sides:** Histos always writes `"fromSide": "right"` and `"toSide": "left"` on dependency edges, and rewrites them on every save. Both are optional in JSON Canvas, but when they're missing Obsidian picks a side the first time it saves the file, based on where the cards happen to be at that moment — top/bottom on a tall board — and then keeps it forever, even after the cards move. Edges between anything other than two cards (e.g. an arrow you drew to a text note) are left as they are.

**Redundant edges:** when a longer path already implies an edge (A → B → C makes a direct A → C redundant), `histos arrange` removes it from the canvas and records A in C's `implied_dependencies` frontmatter (see below). That changes nothing about what's blocked — C can't leave Blocked before B is approved, and B can't before A — it just stops drawing the same dependency twice.

## `.md` frontmatter

Whatever Obsidian/JSON Canvas doesn't interpret natively lives as YAML frontmatter on each card — never in the `.canvas`. Fields Histos doesn't know (your own Obsidian properties) are allowed and never touched.

| Field | Type | Written by | Notes |
|---|---|---|---|
| `description` | string | `add-card --description`, `describe --text` | one line, summarizes the card; never touches the body, so it doesn't go through `propose`/`approve` |
| `sources` | list of paths | `describe --sources` | external files (`.txt`, `.md`, `.tex`, `.docx`) with reference material; replaces the whole list. `histos context` includes their text |
| `assigned_to` | `"agent"` \| `"human"` | `assign --by` | |
| `worker` | string | `assign --worker` | who works an In progress card (`parent`, `sub-cap3`...); cleared by `reject`, kept by `approve` as a record |
| `status_note` | string | `reject --feedback` | the reviewer's feedback; `histos context` shows it on that same card |
| `implied_dependencies` | list of card ids | `arrange` | dependencies whose arrow it removed because a longer path already implies them; `histos context` still includes them, labeled "implied" |
| `proposed_tier` | `fast` \| `exec` \| `reasoning` | `classify` | see [`histos.config.yaml`](#histosconfigyaml) |
| `proposed_model` | string | `model --proposed` | the concrete model the agent proposes — free text, Histos doesn't know which models exist |
| `approved_model` | string | `model --approved --authorized` | the human's choice, which may differ from the proposed one. A `classify` that changes the tier clears both models |
| `eval_results` | mapping | `propose` | the last evals run: `passed`, `attempt` (for the 3-attempt cap), `at`, and `checks` (each with `name`, `passed`, and `error`/`detail`) |
| `content_hash` | 64 hex characters | `add-card`, `approve`, `accept-edit` | SHA-256 of the body as Histos last wrote it legitimately; the `content_untouched` eval compares against it |
| `estimate` | mapping | `status`, `classify` | the card's estimate while it is open: `agent_hours` and `review_hours`, each `{median, p80, basis}` (hours, 2 decimals; `null` when there isn't enough history), plus `at`, the date. `p80` is "if it goes badly": 4 in 5 similar cards finished sooner. **`review_hours` is computed from the human's *active* review time** -- the calendar time a card waited, minus the stretches the human was away between `histos pause` and their next decision -- not from the calendar time. Only rewritten when the rounded numbers change |
| `estimated_duration_hours` | number | `status`, `classify` | agent median + review median (the active review time above); `null` when either is missing |
| `actual_duration_hours` | number | — | reserved; no command sets it yet |

`status` is deliberately not here: it lives as `color` on the canvas so the same data doesn't have two sources of truth.

A card from [`examples/sample-paper/`](../examples/sample-paper/), in review after passing its evals:

```yaml
---
description: Compare the three main approaches and their trade-offs
assigned_to: agent
content_hash: 3460715e5c649718a4248079f4953da51618aafbf597006f043b12dc78b8cd00
worker: parent
proposed_tier: reasoning
proposed_model: Opus 5.5
approved_model: Opus 5.5
eval_results:
  passed: true
  attempt: 1
  at: '2026-10-16T14:05:45+02:00'
  checks:
  - name: no_direct_writes
    passed: true
    detail: content/ untouched
  - name: no_placeholders
    passed: true
    detail: no placeholders
---
```

## `histos.config.yaml`

Per-vault settings, created by `histos init` (or `init --add-config` for an older vault). Without it, Histos behaves like v2: no tiers, no evals. Only the human edits it — the agent's own filter shouldn't be something the agent can relax — and Claude Code's deny list covers it.

```yaml
tiers:
  - name: reasoning
    match: any
    heuristics: ["architecture_terms_present", "debugging_terms_present",
                 "multi_step_reasoning_implied", "token_count >= 3000"]
  - name: exec
    match: any
    heuristics: ["code_blocks_present", "file_operations_mentioned"]
  - name: fast
    match: all
    heuristics: ["token_count < 300", "dependency_count <= 1", "no_code_blocks",
                 "not file_operations_mentioned"]
terms:                       # optional: words added to the built-in lists
  architecture: ["ontology"]
evals:
  enabled: true
  path: evals/               # relative, inside the vault
  run_on: propose
```

**Tiers are fixed:** `fast`, `exec` and `reasoning` must each appear exactly once — the file tunes their rules, not which tiers exist. Histos never maps a tier to a model: the agent does, for its own platform.

**How a tier is picked** (`histos classify`): tiers are checked `reasoning` → `exec` → `fast`, whatever their order in the file. A tier matches by its `match` — `any` (one condition holds, the default) or `all` (every one does); a tier with no conditions never matches. The first match wins; if none matches, `exec`. The output explains every tier it checked:

```
method -> fast
  reasoning (any): no match -- no architecture terms; no debugging terms; no multi-step wording; token_count = 81
  exec (any): no match -- no code blocks; no file operations terms
  fast (all): match -- token_count = 81; dependency_count = 1; no code blocks; no file operations terms
```

**Conditions** are a closed catalog — no expressions, no `eval()`. Three forms: `"name"`, `"not name"`, and `"measure <op> number"` with `<`, `<=`, `>`, `>=`, `==`.

| Condition | Kind | What it measures | Measured on |
|---|---|---|---|
| `token_count` | measure | approximate tokens: characters ÷ 4 | full context |
| `word_count` | measure | words | full context |
| `dependency_count` | measure | direct and implied dependencies | — |
| `source_count` | measure | registered sources | — |
| `code_blocks_present` | yes/no | a fenced or indented code block | full context |
| `math_symbols_present` | yes/no | `$...$`, `\frac`, `∑`, `≤` and the like | full context |
| `file_operations_mentioned` | yes/no | file terms (folder, path, `.csv`, `.py`...) | card text |
| `architecture_terms_present` | yes/no | design, structure, methodology, decisions, synthesis... | card text |
| `debugging_terms_present` | yes/no | bugs, tracebacks, failures | card text |
| `multi_step_reasoning_implied` | yes/no | 3+ listed steps, or 2+ sequence words ("first... then...") | card text |

`no_code_blocks` and `no_math_symbols` are accepted as aliases of their negation. **Card text** is the card's own title, description, feedback and body — so a dependency that mentions "debugging" doesn't make this card `reasoning`. **Full context** is what `histos context` bundles for the card (dependencies' approved content, sources), minus `PROJECT.md`/`ARCHITECTURE.md`, which are the same for every card. Terms are matched as whole words (plurals included), ignoring case and accents, in English and Spanish; `terms:` adds to the built-in lists, never replaces them.

The default rules were calibrated on ~400 real cards, writing and code: about 13 % `fast`, 57 % `exec` (half of them by default) and 30 % `reasoning`. With one-line descriptions the signal is weak — the tier is a suggestion with its reason, and the human approves the model. `scripts/calibrate_tiers.py` measures how a config would split your own vaults, read-only.

## Evals

Each `.yaml`/`.yml` file in `evals/` is a list of evals; `histos propose` runs every one that applies to the card before the card can turn yellow. Files are read in alphabetical order; anything else in the folder is ignored. Only the human edits this folder (Claude Code's deny list covers it).

```yaml
- name: min_word_count          # unique across the folder; shown in eval_results and diff
  check: word_count             # one check from the catalog below
  min: 300                      # its parameters, and nothing else
  error: "A chapter needs at least 300 words"   # optional: each check has a default message
  only: ["cap*"]                # optional: card id patterns it applies to
  except: ["cap0"]              # optional
```

| `check` | Parameters | Passes when |
|---|---|---|
| `word_count` | `min`, `max` (at least one) | the draft's word count is within bounds |
| `no_placeholders` | `patterns` (optional) | no leftover markers: by default `TODO`, `TBD`, `FIXME`, `XXX`, `lorem ipsum`, `[...]`, `[citation needed]`, `[cita requerida]`. ALL-CAPS markers match case-sensitively as whole words ("todo" is ordinary Spanish), the rest anywhere |
| `required_headings` | `headings` | the draft has every one of these headings, at any level. Each can be a list of acceptable spellings (`["## Objetivo", "## Goal"]`, any one counts); case, spacing and accents don't matter |
| `min_section_words` | `sections`: a list of `{heading, min}` | each of these sections (from its heading to the next one of the same or a higher level) has at least `min` words; a missing section counts as 0. `heading` takes alternatives like above |
| `content_untouched` | — | nothing changed `content/` behind Histos's back: each card's body still matches its `content_hash` (cards from before v3 are compared with their copy in `approved/`, or pass with "no baseline") |

**On `propose`:** every applicable eval runs — no stopping at the first failure, so the agent fixes everything in one retry. If any fails, there's no proposal, the card stays In progress, and the output says what to fix. A check that crashes counts as a failure, never as a silent pass. An invalid `evals/` folder or config blocks `propose` with its error, without spending an attempt.

**Three attempts:** `eval_results.attempt` counts consecutive failures in the current cycle; it starts over after a proposal that passes (and so after a rejection). After the third failure `propose` refuses until the human runs `histos retry <id>`.

**Hand edits:** if you edit a card's body yourself in Obsidian, `content_untouched` flags it — run `histos accept-edit <id>` to make your version the legitimate one.

**Guide files:** `histos guide propose` runs the evals whose `only` names the file (`only: ["PROJECT.md"]`) — an eval without `only` never applies to a guide, so a vault's card evals don't start checking `PROJECT.md` by surprise. A failing draft isn't saved; there's no attempt limit, since a guide change is proposed with the human in the conversation. `histos guide diff` shows what the evals said, and `histos eval PROJECT.md --file <draft>` is the dry run.

`histos init` creates `evals/basics.yaml` (`content_untouched` and `no_placeholders`, active), `evals/examples.yaml` (a word minimum and required headings, commented out: they depend on each project) and `evals/guides.yaml`: the required sections of `PROJECT.md` (in Spanish or English — goal, deliverable, audience, out of scope, done when, constraints, *what I understood*, *what I'd change and why*, decisions), at least 60 and 30 words in the two sections the agent writes itself, and no placeholders in either guide. `histos init --add-config` adds `evals/guides.yaml` to an existing vault too: it only applies to the guides, so it can't change how any card is checked.

## Guidance files

`PROJECT.md` (what the project is) and `ARCHITECTURE.md` (how it's written: style, conventions, stack) are optional; when they exist, `histos context` appends both, in that order. Only the human changes them: the agent proposes a new version with `histos guide propose <file> --file <draft>`, and the human runs `histos guide approve` (the previous version goes to `approved/guides/<name>-<date-time>.md`) or `histos guide reject --feedback "..."` (which `histos context` then shows).

**Decisions.** When the human rejects a plan or a guide change *with* `--feedback`, Histos keeps that feedback as a decision, so no agent proposes again what was already turned down:

```markdown
## Decisiones
- 2026-11-09 · plan rejected: Split cod-a in two; the release can't depend on a card that big.
- 2026-11-09 · PROJECT.md change rejected: No cambies el alcance: el GUI queda fuera de la v3.1.
```

It's the one time Histos writes into `PROJECT.md` outside `guide approve`, so it's narrow: only the human's `plan reject` and `guide reject` do it, only with the human's own text, appending one dated line at the end of the decisions section (`## Decisiones` or `## Decisions`, any level) and touching nothing else; the previous version is kept in `approved/guides/`. A pending `PROJECT.md` change with that section gets the line too, so approving it doesn't lose it. If `PROJECT.md` doesn't exist or has no decisions section, the line goes to `.histos/decisions.md` instead, and `histos context` shows it until the agent carries it into `PROJECT.md`. A rejection without feedback records nothing.

## Plans

A plan is a whole card table proposed at once: `histos plan propose --file <plan.yaml>` (agent), `histos plan diff` (anyone), then `histos plan approve` or `histos plan reject --feedback "..."` (human). No card exists until the plan is approved.

```yaml
summary: >
  How the work is cut and why -- the first thing the human reads.
cards:
  - id: dec-format                  # required; same rules as add-card
    title: Decide the format        # required
    description: One line.          # optional
    done_when: The format is approved and cod-format can implement it without questions.   # required
  - id: cod-format
    title: Implement the format
    done_when: Every command writes it, with tests.
    depends_on: [dec-format]        # cards in this plan, or already on the board
```

- **No tier in the plan:** a card is classified right before it's worked (`histos classify`), since its tier depends on the approved content of its dependencies.
- **Refused on propose** (and checked again on approve, in case the board changed): unknown keys (a typo like `depend_on` never passes silently), a missing `summary`, `id`, `title` or `done_when`, invalid or repeated ids, ids already on the board, dependencies that exist nowhere, and cycles. All errors are listed at once.
- **`plan approve`** creates every card in dependency order with one canvas save — all or nothing: if anything fails, no card and no file is left behind, and an existing `content/<id>.md` is never overwritten. Approving the plan is the authorization for its dependencies, so no `--authorized` is involved. The plan is kept in `approved/plans/<date-time>.yaml`.
- **`done_when`** goes into the card's frontmatter and initial body, and `histos context` shows it; `add-card --done-when "..."` sets it on a single card.
- **Levels and warnings:** `histos plan diff` shows the plan by levels (level 1 can start once the plan is approved; a dependency on an unapproved board card is marked `(waits for <id>)`) and then its warnings, or `No warnings.`. `plan propose` prints the same warnings to stderr without failing. There are three: a loose card (in a plan of more than one card, it depends on nothing and nothing depends on it), a card with more than 5 dependencies, and a vague `done_when` (under 5 words, or an empty phrase like "done" or "funciona"). They never block approval: the human decides.
- One plan is pending at a time: proposing another replaces it. A rejection's feedback is shown by `histos plan diff` until the next plan is proposed.

## Event log

Every command that changes the vault records what it did in `.histos/events.jsonl`: one JSON object per line, append-only, written inside the vault lock. It's the history that estimates, the critical path with real durations and the project report are built from, so it records generously — including how long a card waited for the human's review. Nothing leaves your machine.

```json
{"v": 1, "ts": "2026-11-08T16:42:07.312Z", "event": "approved", "card": "cod-plan",
 "actor": "human", "worker": "parent", "data": {"words": 812, "lines": 96},
 "transitions": [{"card": "cod-plan", "from": "Proposal pending review", "to": "Approved"},
                 {"card": "pru-plan", "from": "Blocked", "to": "Backlog"}]}
```

| Field | What it is |
|---|---|
| `v` | format version (1) |
| `ts` | when, in UTC with milliseconds — durations are differences between events |
| `event` | what happened (table below) |
| `card` | the card, or `null` for vault-wide events |
| `actor` | `human` for the human's commands (`approve`, `reject`, `retry`, `accept-edit`, `guide approve/reject`, `init`, `arrange`, `status`) and everything the desktop app does; `agent` for the rest |
| `worker` | the card's `worker` at that moment, if any — tells the parent's time from a subagent's |
| `data` | what's specific to the event |
| `transitions` | every card whose status the command changed — this one *or any other*: approving a card records the dependents it unblocked. On the command's last event |

| `event` | Recorded by | `data` |
|---|---|---|
| `vault_created` | `init` | `version` |
| `config_added` | `init --add-config`, when it added something | `files` |
| `card_created` | `add-card` | `title`, `depends_on` |
| `dependency_added` | `link` | `depends_on` |
| `described` | `describe` | `fields` (names only) |
| `assigned` | `assign`, one per card | `by`, `takeover`, `previous_worker` |
| `classified` | `classify` (not `--dry-run`) | `tier`, `previous_tier`, `model_cleared` |
| `model_proposed` / `model_approved` / `model_cleared` | `model` | `model` |
| `proposed` | `propose` that passed the evals | `attempt` (or `null` without evals), `words`, `lines` |
| `proposal_refused` | `propose` that failed the evals | `attempt`, `failed` (eval names), `words`, `lines` |
| `approved` / `rejected` | `approve` / `reject` | `words`, `lines` of the approved text / `feedback` |
| `retry` / `edit_accepted` | `retry` / `accept-edit` | — |
| `guide_proposed` / `guide_approved` / `guide_rejected` | `guide ...` | `file`, plus `words`/`lines`, or `feedback` and `recorded_in` (where the decision went, or `null`) |
| `plan_proposed` / `plan_approved` / `plan_rejected` | `plan ...` | `cards`, plus `feedback` and `recorded_in` on a rejection |
| `arranged` | `arrange` | `pruned` |
| `state_recomputed` | any command whose only effect was a status change — e.g. `status` unblocking cards. With `seen_outside_histos: true`: colors changed by hand in Obsidian since the last recorded command, recorded with the time Histos saw them | — / `seen_outside_histos` |

Read-only commands (`status` when nothing changed, `context`, `diff`, `validate`, `eval`) record nothing, and the text of proposals isn't copied into the log — it's already in `approved/`.

**Reliability:** a session's events are appended in one write with `fsync`. If the machine dies mid-line, the cut-off last line is ignored and `validate` warns about it; any other broken line is a `validate` error. If recording fails (a full disk), the command warns and still succeeds: the vault change already happened.

**The rest of `.histos/`:** `vault.json` holds the vault's id (a UUID, so its history stays recognizable if the folder moves) and `colors.json` each card's color as of the last recorded command (how changes made in Obsidian are noticed). Outside the vault, `~/.histos/vaults.json` lists every vault that recorded an event, so later versions can learn from all your projects without asking where they are; set `HISTOS_HOME` to keep it somewhere else. Next to it, `~/.histos/pauses.jsonl` records `histos pause` (`{"event": "pause", "ts": ...}`) and the decision that ended it (`{"event": "resume", "ts": ..., "by": "approve"}`): one pause per person, for every vault, so review time can leave out the hours you were away.

If you keep a vault in git, commit `.histos/` with it — it's the project's history.

## Minimal canvas

```jsonc
{
  "nodes": [
    { "id": "cap1", "type": "file", "x": 0,    "y": 0, "width": 250, "height": 100,
      "file": "content/cap1.md", "color": "4" },        // Approved
    { "id": "cap2", "type": "file", "x": 320,  "y": 0, "width": 250, "height": 100,
```
